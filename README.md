**🔍 Security Testing Highlight**

During an authorized security review carried out with the owner's consent, I identified that an application had exposed API keys directly in client-side code. If left unaddressed, this could have exposed the owner to significant unplanned costs through unauthorized use of billed services. I reported the finding and worked with the owner to move the affected keys to secure server-side handling, removing them from anything a client could inspect. It's a concrete example of how a small, overlooked detail in how credentials are handled can carry real financial risk, and why treating security as part of the architecture rather than an afterthought matters in practice, not just in theory.

### 🐾 LeakHound

**Secrets Scanner CLI**

[View Repository →](https://github.com/rhizzyxvaici171-cloud/leakhound)

LeakHound is a command-line tool that scans a codebase for accidentally committed API keys, tokens, and credentials before they end up in a public repo. It grew directly out of a real finding: during an authorized security review, I discovered an application with API keys exposed in client-side code, the kind of oversight that can quietly turn into a large, unplanned bill. LeakHound is the tool I wished had been watching that codebase from day one.

It detects provider-specific formats (AWS, GitHub, Slack, Stripe, Google), private key blocks, JWTs, and generic assigned secrets, plus a Shannon-entropy fallback for custom formats that don't match a known pattern. It ships as an installable package with a `leakhound` command, a full test suite, and a GitHub Actions pipeline that tests the tool and then runs it against its own source on every push.

**Focus:** Secret detection · Static analysis · CI/CD security gating · Defensive tooling

### ⚔️ SkillForge: Competitive Skill Arena

SkillForge is a full-stack competitive skill platform where users prove their abilities through timed tests and skill-based games, compete against one another, and progress through a structured ranking and reward system.

**Stack:** ![React](https://img.shields.io/badge/-React-61DAFB?style=flat-square&logo=react&logoColor=black) ![Vite](https://img.shields.io/badge/-Vite-646CFF?style=flat-square&logo=vite&logoColor=white) ![TypeScript](https://img.shields.io/badge/-TypeScript-3178C6?style=flat-square&logo=typescript&logoColor=white) ![Tailwind CSS](https://img.shields.io/badge/-Tailwind_CSS-06B6D4?style=flat-square&logo=tailwindcss&logoColor=white) ![Supabase](https://img.shields.io/badge/-Supabase-3ECF8E?style=flat-square&logo=supabase&logoColor=white) ![PostgreSQL](https://img.shields.io/badge/-PostgreSQL-4169E1?style=flat-square&logo=postgresql&logoColor=white)

SkillForge is being built around a simple principle:

> Competence should be demonstrated, measured, and earned, not simply claimed.

But the interesting engineering challenge isn't the leaderboard UI. It's making sure the system itself can be trusted.

**🔒 Security-First Architecture**

The client is never trusted with authoritative game or competition data. Quiz answer keys are stored in a database table with zero client-readable RLS policies. Even an authenticated administrator cannot retrieve the answer keys through the browser; only the server-side grading function can access them.

Game scores follow the same architecture. The browser submits raw gameplay data such as reaction times, recalled sequences, and gameplay events. It does not submit the final score. A Supabase Edge Function validates the raw data and calculates the authoritative result server-side.

**🛡️ Database-Level Anti-Cheat**

Security isn't dependent on frontend validation. Attempt limits are recomputed and enforced through PostgreSQL logic rather than trusting values supplied by the client. The system can invalidate attempts based on signals such as implausible reaction times, excessive false starts, invalid attempt counts, and other server/database-side validation rules.

The objective is simple: a user shouldn't be able to modify the browser and rewrite the truth of the competition.

**💰 Idempotent Reward Settlement**

Competition results are calculated dynamically rather than relying on a permanently stored leaderboard table that can become stale. Reward settlement uses locking and idempotent execution. If the same settlement operation runs again, the system detects that it has already been processed and does nothing, preventing accidental double settlement or double rewards.

**📊 Business Rules as Data**

Reward payouts and rank thresholds aren't buried inside application code; they live in versioned database structures. That means future competition seasons can introduce different reward structures, rank thresholds, progression rules, and competition parameters without rewriting historical competition logic. This separates business configuration from application code.

**🧱 Specification Before Implementation**

SkillForge was developed around a locked product specification. Scoring rules, reward amounts, progression thresholds, and other formal product rules were defined before the database engine was built. The backend has gone through 14+ migrations, covering authentication, profiles, competitions, submissions, scoring, RLS, server-side grading, settlement, achievements, an internal currency ledger, and ranking/progression.

The objective wasn't simply to make a prototype work. It was to establish a backend foundation that could support the product as it evolves.

**🎮 Current Challenges**

- **Multiple-choice competitions**: cybersecurity and general knowledge categories, with server-side grading
- **Reaction-time challenge**: a custom-built game where raw reaction data is submitted and the final score is calculated server-side
- **Memory-recall challenge**: a custom-built memory game with its own server-side scoring function

**🚧 Current Status: Active development**

Working end-to-end: authentication, core competition loop, competition submissions, server-side grading, two game-based challenge types, scoring architecture, security controls, and reward/settlement foundations.

Currently being developed: administrative interface, public deployment, further competition types, and product refinement.

### 🛍️ FitSure: AR-Powered Shopping Confidence Platform

FitSure is a consumer and enterprise e-commerce technology concept designed to reduce uncertainty before purchase.

The core idea is simple:

> Help shoppers understand whether a product is right for them before they buy it.

FitSure explores how augmented reality, personalization, verified customer evidence, and intelligent recommendations can improve the online shopping experience.

**🎯 The Problem**

Online shoppers often hesitate because product pages cannot fully answer questions such as: will this clothing fit me, how will these shoes look on me, will this product actually suit my needs, what does it look like in a real environment, can I trust the reviews, and what happens if it doesn't meet expectations. This uncertainty contributes to abandoned purchases, poor customer confidence, and avoidable returns.

**🧠 The Product**

FitSure is designed around pre-purchase confidence. The platform explores combining:

- 📱 AR-powered product visualization
- 👕 Virtual apparel try-on
- 👟 Footwear visualization
- 📏 Intelligent size recommendations
- ⭐ Verified buyer photo/video evidence
- 🔍 Trust and product confidence signals
- 🛒 Product discovery and checkout
- 📦 Order and return tracking
- 🏪 Merchant dashboards
- 📊 Seller analytics
- 🔐 Privacy-conscious body-data handling

**🪞 AR Shopping Experience**

A central component is the ability to visualize products before purchasing. Depending on the product category, users could use their device camera to visualize clothing on their body, preview footwear, understand product proportions, visualize selected home products in their environment, and compare products before purchasing.

The long-term architecture explores a hybrid approach where appropriate processing can happen on-device, while cloud infrastructure handles functionality that requires greater computational resources.

**👤 Personalized Recommendations**

FitSure isn't intended to simply display products. The platform is designed to learn from the shopping journey:

**Viewed → Tried → Purchased → Kept / Returned**

That feedback loop can improve future recommendations and provide merchants with better insight into what customers actually keep.

**📸 Verified Buyer Evidence**

FitSure explores a stronger form of product review where customer images and videos can be connected to verified purchases, so users see products in more realistic contexts rather than relying entirely on studio photography. The system can also introduce contextual information such as product category, purchase verification, body/context information where appropriate, fit experience, and keep/return outcomes.

**🔐 Privacy by Design**

Because AR and personalization can involve sensitive user information, privacy is treated as a product requirement rather than an afterthought. The concept prioritizes explicit consent, minimal data collection, data deletion controls, secure authentication, biometric/passkey authentication where appropriate, on-device processing where practical, limited retention of body-related data, and GDPR/CCPA-conscious architecture.

**🏪 Merchant Platform**

FitSure also explores the business side of the ecosystem. Merchants could have access to product management, AR asset uploads, customer confidence analytics, product performance, return insights, seller onboarding, and product catalog management.

This creates a potential B2C marketplace plus B2B technology layer, allowing the underlying confidence technology to potentially serve retailers beyond the consumer application.

**🛠️ Product Direction**

The initial product direction focuses on:

**Apparel → Footwear → Home Décor → Beauty → Electronics Accessories → Broader Merchandise**

The objective is to start with categories where purchase uncertainty and returns can create significant value from better product visualization and confidence signals.

**🚧 Current Status: Product planning / pre-build stage**

FitSure is currently being developed at the product-definition and architecture level, with emphasis on validating the problem, defining the MVP, designing the technical architecture, and determining where AR and personalization provide genuine customer value.

Core thesis:

> Don't just help people find products. Help them feel confident buying them.

## 🧪 Security-Minded Engineering

One of the areas I particularly enjoy is examining the boundary between application functionality and security.

For example, a normal developer might ask: *"Does the leaderboard display correctly?"*

A normal application might ask: *"Did the user submit a score?"*
